# Shader declarations and serialized program associations

The offline commands use the standard library and do not execute shaders or launch an editor/game. The native observation command additionally loads the pinned official DLL in an isolated process; it does not render or launch the game.

```powershell
aow4mod effect-variants '<library.clb>' --locator '[LIBRARY]EFFECT\0' --stage 1 --pass-id 1 --require NOBONES --require NOUV2 --limit 5
aow4mod dxil-inspect '<DXIL program or concatenated program pool.bin>' --vertex-profile pnuvct52 --limit 3
aow4mod effect-programs '<library.clb>' --locator '[LIBRARY]EFFECT\0' --pass-index 0 --stage 1 --require NOBONES --require NOUV2 --vertex-profile pnuvct52 --limit 3
aow4mod native-effect-programs '<library.clb>' --locator '[LIBRARY]EFFECT\0' --output '<new witness directory>'
```

`effect-variants` reads the observed TREEffectResource/function/code metadata, reports each function's own feature-name/mask table, and filters serialized variants using explicit required/forbidden features. Stage 0 is pixel and 1 is vertex. Features absent from a function cannot satisfy a required condition. Function and variant order, full masks and unmapped bits remain visible. A query returning zero candidates is not compatibility evidence. Dynamic/static material expressions and renderer state are not evaluated. The tested DefaultMaterial pass 1 contains 16 vertex declarations satisfying NOBONES and NOUV2; these are declarations, not proof of the actual chosen variant.

`dxil-inspect` accepts an exact sequence of DXBC/DXIL containers, bounded to 64 MiB/4096 containers, 64 parts/container and 256 ISG1 parameters. It checks container/part/program/bitcode ranges, overlapping or duplicate parts, signature bounds, names, duplicate semantics, component masks and padding. Arbitrary gaps/trailing data are rejected instead of searching for a convenient magic marker. Unsupported/missing signature information is not silently accepted as vertex coverage. The parser uses Microsoft's DXIL container/signature structure definitions, without executing or validating LLVM bitcode or authenticating container hashes.

Optional profile checks compare used input semantic/component masks against the observed PNUV32 or PNUVCT52 layouts; known VertexID/InstanceID inputs are generated by the system. Bone attributes, UV1, missing components, unknown streams and non-float signature types remain findings. Unused inputs do not require supplied vertex components. This does not establish native DXGI conversion or actual renderer bindings. Zero vertex programs is explicitly not evaluated.

`effect-programs` decodes the observed 24-byte mode-2 CLB data reference as a bounded LZ4 block, then maps each 72-byte pass/stage lookup record to one exact DXIL container offset and length. Bytes 32..63 are a little-endian 256-bit feature mask indexed by the effect's ordered `FFeatureNames` vector (field 70). The first 32 bytes remain opaque. `--key` accepts all 64 prefix bytes as 128 hexadecimal digits; `--require`/`--forbid` filter the declared feature names case-insensitively. Required absent names select no rows; unknown mask bits remain explicit. Do not substitute a function's local mask bits for the effect's global name indices.

Identical duplicate records preserve their order and `duplicate_of` index; conflicting records with the same full prefix are rejected. The tested original System_Effects library contains 106 identical duplicates across five effects, so duplicates alone do not imply corruption. Inconsistent record counts, unsupported compression flags and invalid program boundaries are rejected. Stages 0/1 are checked against pixel/vertex program kinds; any other populated stage remains explicitly unverified. Filtering/pagination does not expand coverage, and zero matching rows or vertex programs is not a successful compatibility check.

`native-effect-programs` freezes the loaded CPU program pool and every nonempty pass/stage lookup table, then compares them with independent file decoding. Version 2 also reads the actual ordered feature names through reviewed native string-vector accessors and requires them to match the serialized vector. Its output includes hashes, DLL/backend binding and native diagnostics; it can be rechecked offline with `native_effect_programs.validate`. Historical version 1 covers pool/tables only and cannot carry a native feature-name claim. The command observes existing loaded data without activating resources again. Matching CPU data proves the serialized association, but does not show which key a material or renderer chooses.

All 87 effects in the tested original System_Effects library decode: 2,804 program containers and 4,137 lookup records, with no unmapped feature bits. DefaultMaterial contains 1,434 contiguous containers (1,170 pixel and 264 vertex programs), 11 passes and 1,940 lookup records in 22 nonempty tables; every program is referenced. Independent native observations match the pool, every table and feature-name order for DefaultMaterial, an effect with 88 identical duplicates, and an effect with no feature names.

For DefaultMaterial's pass 0, requiring NOBONES and NOUV2 selects 16 vertex lookup records, all of whose declared inputs fit PNUVCT52. This is an intended-feature query, not evidence that the material selects those conditions at runtime. Across the whole unfiltered pool PNUVCT52 covers 56 unique vertex programs; 208 require additional/unverified inputs. Function declaration order is not assumed to match lookup order. Do not clear model/material draft gates using these counts or a filtered variant list. The earlier null effect getter on copied materials was traced to a missing CLB `FDependencies` declaration: adding `SYSTEM_EFFECTS.CLB` resolves the actual effect pointer. This is now automatic in the Default model/material recipe, with staged repair available through `clb-import-plan/apply`. Actual material feature evaluation and renderer choice remain unverified.
