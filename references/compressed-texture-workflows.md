# Compressed texture and DDS workflow

## Pinned community toolchain

```powershell
aow4mod texture-toolchain --download --output '<new private tool directory>' --proxy 'http://127.0.0.1:10808'
aow4mod texture-toolchain --texconv '<tool directory/texconv.exe>'
```

Downloads happen only through this explicit command. The adapter pins Microsoft's official [DirectXTex may2026 release](https://github.com/microsoft/DirectXTex/releases/tag/may2026), x64 `texconv.exe` version 2026.5.8.1, SHA-256 `dcfdec10244e02cf5037fba089c55fb7e1326b1c8181742d77d15fa5cb5eef06` (also published in GitHub release metadata). Unknown executable hashes fail before execution. The tool stays in the caller's private directory; it is not installed globally or committed into the Skill. Download output cannot be inside the installed game or real Mods directory.

Every conversion uses argument arrays, a fresh working/output directory, captured stdout/stderr, a bounded process lifetime and before/after executable hashes. Encoding explicitly uses CPU mode (`-nogpu`, `-singleproc`); it does not initialize the game's renderer. References: Microsoft's [texconv](https://github.com/microsoft/DirectXTex/wiki/Texconv), [DDS layout guide](https://learn.microsoft.com/en-us/windows/win32/direct3ddds/dx-graphics-dds-pguide), and [DX10 header](https://learn.microsoft.com/en-us/windows/win32/direct3ddds/dds-header-dxt10).

## Compress PNG and existing role-aware mips

```powershell
aow4mod texture-compress-plan '<Mod>' --image '<color.png>' --namespace OWN_BC7 --codec bc7 --role color --mips full --texconv '<texconv.exe>' --max-error 32 --output '<plan.json>'
aow4mod texture-compress-plan '<Mod>' --image '<normal-xyz.png>' --namespace OWN_BC5 --codec bc5s --role normal-xyz --mips full --texconv '<texconv.exe>' --max-normal-angle 8 --output '<normal-plan.json>'
aow4mod texture-dds-apply '<plan.json>' --output '<new staged Mod>'
```

The input uses the [ordinary PNG/mip rules](texture-level-workflows.md), with base dimensions divisible by four and no automatic resize. Color/data codecs are BC1, BC3 and BC7. Color uses typed sRGB variants; data uses Linear. BC1 refuses smooth source alpha rather than silently discarding it. The tool creates an uncompressed DDS with the exact generated mip chain before encoding; target format, dimensions and count must remain unchanged. A deliberate distinct-color-per-level control confirmed that texconv preserves the supplied complete chain.

`bc5s` compresses unsigned RGB XYZ normals into signed XY BC5_SNORM (DXGI 84/native 172), using explicit x2-bias conversion. It requires opaque positive-Z-hemisphere inputs because two channels cannot retain negative Z or alpha. Quality compares reconstructed positive Z against the original normalized XYZ direction; the caller's axis convention is preserved. Source normal mips are generated by vector filtering before compression.

Loss is measured, not assumed absent. The default color limit is a maximum absolute RGBA channel error of 32 code values; the normal limit is eight degrees. Both are explicit parameters. Every mip has a report. A tested BC7 sample had max error 1; a tested BC5 sample had max angular error about 0.13 degrees. BC1/BC3 solid-color controls had max error 3. These examples do not promise those errors for other artwork. Tight limits can reject an otherwise structurally valid encoded result.

## Import an author-provided DDS

```powershell
aow4mod texture-dds-plan '<Mod>' --dds '<encoded.dds>' --namespace OWN_DDS --role color --texconv '<texconv.exe>' --output '<plan.json>'
aow4mod texture-dds-apply '<plan.json>' --output '<new staged Mod>'
```

Supported typed 2D formats are BC1/BC3 UNORM or sRGB, BC5 UNORM/SNORM and BC7 UNORM/sRGB. Reviewed legacy DXT1/DXT5/ATI2/BC5 FourCC inputs are supported as Linear data unless their container explicitly provides sRGB typing. DDS imports are bounded to 2048×2048, 64 MiB and 12 levels, exact calculated block lengths and no trailing bytes. Arrays, cubemaps, volumes, typeless/HDR formats, premultiplied/custom alpha and inconsistent flags/pitch/mips fail. Roles are `color`, `data`, or `normal-xy-snorm` and must match the actual metadata.

The base dimension constraint applies to the real imported texture; small sub-4×4 last mip levels remain valid. Per-level single-image DDS views used solely for CPU decoding are not imported as independent game textures. Pillow's BC1/BC3 decoder uses a legacy DXT header view while the original typed/sRGB metadata and block bytes stay bound.

## What is verified

1. Official native CLB compilation and a separate file reload preserve every requested field/member. The actual CLB's bounded stream decoder independently compares **all compressed block bytes**, dimensions, format, color space and mip count with the DDS.
2. Each mip is decoded by both Pillow and the pinned DirectXTex tool. Their meaningful channel results must agree within one code value. BC5 compares XY; its unused B/alpha channels are not used as a normal direction.
3. PNG compression adds source/reference/mip and loss-bound replay; apply recomputes the original mip policy, block comparison, decoder results and measured quality before staging.
4. The existing material/texture-pointer and protocol-8 build checks include these texture objects and their complete compressed surface data. Default normal/diffuse color-space constraints remain.

The game's PNG writer accepts RGBA8 only. Therefore reports explicitly retain `native_pixel_decode_verified=false` and `gpu_verified=false`: native container/block/object preservation and independent CPU decoding are different evidence. No engine compressed-pixel or GPU rendering claim is made. Existing model/material variant gates stay open. Input DDS/author receipts are retained under `SourceImages/<namespace>/` and excluded from runtime builds.

The static asset example accepts `--compression bc1|bc3|bc7 --texconv <path>`; an optional normal map then uses BC5_SNORM.
